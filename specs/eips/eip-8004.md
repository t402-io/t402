## Abstract

This EIP defines three on-chain registries for AI agents:

1. **Identity Registry** — Register agent identities with an owner, wallet address, and off-chain metadata URI
2. **Reputation Registry** — Collect structured feedback (value + tags) from clients who interacted with the agent
3. **Validation Registry** — Third-party validators attest to agent behavior and capabilities

Together, these registries enable **trustworthy agent-to-agent commerce** by providing verifiable identity, Sybil-resistant reputation, and independent validation — all queryable on-chain.

## Motivation

As AI agents increasingly participate in economic transactions (paying for APIs, purchasing compute, accessing data), there is no standard way to:

- Verify that an agent is who it claims to be
- Check an agent's track record before transacting
- Get independent validation of an agent's capabilities

Without these primitives, agent-to-agent commerce relies on implicit trust or centralized gatekeepers. ERC-8004 provides decentralized alternatives.

### Use Cases

- **Payment protocols (T402, x402):** Before paying an agent's API, check its reputation score and identity
- **MCP/A2A discovery:** Agents advertise capabilities via their registration file; clients verify before connecting
- **Marketplace trust:** Agent marketplaces display verified reputation scores instead of self-reported ratings
- **Compliance:** Validators can attest that agents meet specific regulatory or safety requirements

### Identity Registry

```solidity
interface IERC8004Identity {
    /// @notice Register a new agent
    /// @param agentURI URI pointing to the agent's registration file (JSON)
    /// @param agentWallet Address that receives payments for this agent
    /// @param metadata Optional key-value metadata entries
    /// @return agentId The assigned agent identifier
    function registerAgent(
        string calldata agentURI,
        address agentWallet,
        MetadataEntry[] calldata metadata
    ) external returns (uint256 agentId);

    /// @notice Get agent identity by ID
    /// @param agentId The agent identifier
    /// @return owner The agent owner address
    /// @return agentURI The registration file URI
    /// @return agentWallet The payment wallet address
    function getAgent(uint256 agentId)
        external view returns (address owner, string memory agentURI, address agentWallet);

    /// @notice Update agent URI
    function updateAgentURI(uint256 agentId, string calldata newURI) external;

    /// @notice Update agent wallet
    function updateAgentWallet(uint256 agentId, address newWallet) external;

    /// @notice Deactivate an agent (owner only)
    function deactivateAgent(uint256 agentId) external;

    struct MetadataEntry {
        string metadataKey;
        bytes metadataValue;
    }

    event AgentRegistered(uint256 indexed agentId, address indexed owner, string agentURI, address agentWallet);
    event AgentURIUpdated(uint256 indexed agentId, string newURI);
    event AgentWalletUpdated(uint256 indexed agentId, address newWallet);
    event AgentDeactivated(uint256 indexed agentId);
}
```

### Registration File (Off-Chain JSON)

The `agentURI` MUST point to a JSON file conforming to this schema:

```json
{
  "type": "ai-agent",
  "name": "My Agent",
  "description": "An AI agent that provides premium data analysis",
  "image": "https://example.com/agent-avatar.png",
  "services": [
    {
      "name": "Data Analysis API",
      "endpoint": "https://api.example.com/analyze",
      "version": "1.0",
      "skills": ["data-analysis", "visualization"],
      "domains": ["finance", "research"]
    }
  ],
  "x402Support": true,
  "active": true,
  "registrations": [
    {
      "agentId": 42,
      "agentRegistry": "erc8004:8453:0x1234..."
    }
  ]
}
```

### Reputation Registry

```solidity
interface IERC8004Reputation {
    /// @notice Submit feedback for an agent
    /// @param agentId The agent being reviewed
    /// @param value Feedback score (scaled by valueDecimals)
    /// @param valueDecimals Number of decimal places in value
    /// @param tag1 Primary classification tag
    /// @param tag2 Secondary classification tag
    function submitFeedback(
        uint256 agentId,
        uint256 value,
        uint8 valueDecimals,
        string calldata tag1,
        string calldata tag2
    ) external;

    /// @notice Get aggregated reputation summary
    /// @param agentId The agent to query
    /// @return count Number of feedback records
    /// @return summaryValue Aggregated score
    /// @return summaryValueDecimals Decimal precision of summaryValue
    function getReputationSummary(uint256 agentId)
        external view returns (uint256 count, uint256 summaryValue, uint8 summaryValueDecimals);

    /// @notice Get individual feedback record
    function getFeedback(uint256 agentId, uint256 feedbackIndex)
        external view returns (
            uint256 value,
            uint8 valueDecimals,
            string memory tag1,
            string memory tag2,
            bool isRevoked,
            address clientAddress
        );

    /// @notice Revoke previously submitted feedback
    function revokeFeedback(uint256 agentId, uint256 feedbackIndex) external;

    event FeedbackSubmitted(uint256 indexed agentId, address indexed client, uint256 value, string tag1, string tag2);
    event FeedbackRevoked(uint256 indexed agentId, uint256 indexed feedbackIndex);
}
```

### Validation Registry

```solidity
interface IERC8004Validation {
    /// @notice Submit a validation request
    /// @param validatorAddress Address of the validator
    /// @param agentId Agent to validate
    /// @param requestURI URI containing validation criteria
    /// @param requestHash Hash of the validation request
    function requestValidation(
        address validatorAddress,
        uint256 agentId,
        string calldata requestURI,
        bytes32 requestHash
    ) external;

    /// @notice Submit validation response (validator only)
    /// @param agentId Agent being validated
    /// @param response Score 0-100
    /// @param responseHash Hash of detailed response
    /// @param tag Classification tag
    function submitValidation(
        uint256 agentId,
        uint8 response,
        bytes32 responseHash,
        string calldata tag
    ) external;

    /// @notice Get validation status
    function getValidation(address validatorAddress, uint256 agentId)
        external view returns (uint8 response, bytes32 responseHash, string memory tag, uint256 lastUpdate);

    /// @notice Get validation summary for an agent
    function getValidationSummary(uint256 agentId)
        external view returns (uint256 count, uint256 averageResponse);

    event ValidationRequested(address indexed validator, uint256 indexed agentId, string requestURI);
    event ValidationSubmitted(address indexed validator, uint256 indexed agentId, uint8 response, string tag);
}
```

### Agent Registry Identifier

Agents are identified across chains using the format: `erc8004:{chainId}:{contractAddress}`

This follows the CAIP-2 convention used by T402 and x402 for network identification.

## Rationale

### Why Three Separate Registries?

Separation of concerns: identity is controlled by the agent owner, reputation is controlled by clients, and validation is controlled by third-party validators. Combining them into one contract would create governance conflicts.

### Why On-Chain?

- **Immutability:** Reputation cannot be retroactively edited
- **Composability:** Other contracts can query reputation before transacting
- **Censorship resistance:** No single entity controls the registry
- **Cross-chain:** Same agent ID works across all EVM networks via the registry identifier

### Why Tags on Feedback?

Tags enable domain-specific reputation. An agent may be excellent at "data-analysis" but poor at "code-generation." Without tags, a single score would conflate these.

## Backwards Compatibility

This EIP introduces new contracts and does not modify existing standards. It is fully additive.

## Security Considerations

### Sybil Attacks on Reputation
An agent could create multiple wallets to submit positive self-reviews. Mitigations:
- **Trusted reviewer lists:** Clients can filter feedback by trusted addresses
- **Proof of payment:** Feedback can include transaction hashes proving real economic interaction
- **Validation scores:** Independent validators provide a separate trust signal

### Registration File Tampering
The `agentURI` points to mutable off-chain content. The agent owner could change the file after registration. Mitigations:
- Clients SHOULD cache the registration file at query time
- Future versions MAY add content hashing to the identity registry

### Gas Costs
Submitting feedback costs gas. For high-frequency agent interactions, off-chain attestations with on-chain anchoring MAY be used as a scaling solution.
